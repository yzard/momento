# Journal FIFO 与简化审查（2026-09-07）

## 实施更新

以下实现取代后文审查时的“尚未实施”状态：

- 消费者抽出单项执行函数。文件 lease 在函数返回时释放，暂时失败由统一外层记录错误、设置持久化 `retry_at` 并移到 FIFO 尾部；不会因一个暂时错误停止处理其他 ready 操作。无法写入重试状态时向上返回错误，消费者释放 admission 后退避，不伪造入队成功。
- 后台消费者在有源 admission 时读取最早重试时间，释放 admission 后等待通知或到期时间。没有新导入也能重试，不再依赖外部通知。启动一致性恢复仍严格失败上报，不把未完成的回滚当成可安全启动。
- 明确的永久发布/清理失败仍进入失败状态，不在每次消费循环重放；回滚以及保护业务一致性的 discard 失败保留可恢复性并延迟重试。
- 发布/清理/回滚授权读取新增显式 `entry_limit`，恢复调用者传 1，现有多项调用者明确传完整上限。SQL 直接 LIMIT，删除“先读全部再截断”的实现，分配容量也随上限变化。
- 终态压缩和过期记录删除每次各处理最多 32 项，共用原来的事务与诊断格式；保留外部重试收据契约及其过期策略。
- 新增 `file_product_references` 视图，从现有 metadata、face crops、AI input 和 job input 表提供统一的存活文件引用。Journal 不再逐个理解业务表，也不新增另一套需要同步的引用表；业务事务提交后视图立即反映引用变化。
- 业务完成边界继续复用现有事务：已终态的 LLM job 不重复持久化，metadata 成功产物的引用在 discard 时受保护；import 重放复用已提交清理记录。未把提交前回滚和提交后清理混成一个状态，也没有重跑成功业务来催促清理。

新增/更新测试覆盖队头占用后续仍可消费、无新通知的到期重试、回滚修复后重试、32 项分页维护、已有成功产物保护、FIFO 和重复导入。仅本地实现与验证，未部署 NAS，也没有宣称实际磁盘吞吐倍数。

**部署注意：新增 `retry_at` 字段和引用视图改变了 schema。项目要求无 migration 且严格校验 schema，因此旧数据库不能直接用于此构建；部署前必须明确安排数据库重建与数据保留。此次没有操作生产数据库或删除原图。**

## 本次已实施

- 通用恢复队列按持久化 `recovery_order, id` FIFO 取队头；指定只包含可执行记录的有序索引，避免 SQLite 每次取任务临时排序。
- 全局队尾序号使用 `recovery_order` 索引，避免对所有历史记录扫描 MAX。
- 发布、清理和回滚的正常 checkpoint 不再把操作反复移到队尾。正常进度保留当前位置；显式 yield、重试或新工作入队才追加到尾部。
- 重复导入先检查源清理记录。媒体、路径、文件身份及大小都匹配已提交操作时，复用成功结果，不重新发布 sidecar、不重复创建清理、不触发 metadata 重跑。不同内容或不同 sidecar 不得误判为已完成。
- 路径由其他操作占用时，在 sidecar 发布前返回暂时阻塞；Local/WebDAV 共用这一实现。

这些改动不增加线程、内存队列或迁移脚本，不修改 NAS 数据。ORDER BY 是数据库 FIFO 顺序的声明；测试检查执行计划没有临时排序。

## 原始审查记录（实施状态以上文为准）

### 1. 重试控制流不统一，可能阻塞整个消费者

`src/backend/io/recovery.rs::recover_file_operations` 中有显式 yield-to-tail、直接返回错误、记录失败后返回成功等不同路径；`src/backend/main.rs` 对成功等待通知，对错误延迟一秒重试。结果是相似的可恢复错误有不同的排队/唤醒语义；直接返回错误还可能不断撞到同一队头。

建议统一单项结果为 Completed / Deferred / Failed。消费者只做取队头、执行、结算；Deferred 记录错误与可重试时间并排到尾部，释放资源。队列调度等待最近重试时间或新工作通知。数据库自身不可写时不能假装已成功重新入队，应退避后重读持久化状态。不要另外建立一套内存计时队列。

### 2. 每处理一个文件都重新读取整个剩余操作

`io/journal.rs::verify_file_operation_cleanup` 调用 `load_authorized_entries`，而恢复循环随后 `retain_first_entry()`。发布及回滚也采用相近的全量读取后保留一项路径。多文件操作会重复读取和构造授权数据。

建议分开“验证操作有效”和“读取下一项”，恢复路径 SQL 只返回所需条目；保留现有面向多项调用者的语义，先梳理所有调用者再统一接口。之后再考虑小批量 checkpoint，不应通过跳过逐文件身份验证或持久化来提速。

### 3. 业务完成与文件收尾的边界不清晰

重复 sidecar 的根因正是业务已成功、源清理尚未消费，却又重跑业务。`file_operation_groups` 同时承载发布、业务确认、清理与回滚状态，业务模块还各自持有任务状态。

建议把“已提交的业务结果不可重跑”作为统一规则，源文件删除、临时文件删除只成为独立幂等清理任务。先统一 import；再逐个审核 metadata 和 LLM result，不把所有历史状态一次性折叠成 pending/done。提交之前的回滚与提交之后的清理必须保留区别。

### 4. 终态维护过细

`io/journal.rs` 的维护流程每次选择一个 compaction candidate，分别统计 action/state/cleanup 后再压缩；此外还有重试请求收据的生命周期。每项操作的历史保留成本不低。

建议维护改成有界分页，每页统一结算。清理完成且无引用后，保留最小诊断摘要；不要让历史明细进入 ready FIFO。是否删除对外重试收据必须先审核对应 API 的幂等契约，不能直接删除。

### 5. 文件系统与业务表耦合过深

`queries::file_operations::SELECT_DERIVED_PRODUCT_DISCARD_ENTRIES` 直接查询 metadata、faces、AI inputs 等业务表判断能否删除。每新增一种产物，都可能遗漏这一清理保护。

建议产物提交时统一记录所属操作及引用，Journal 只处理文件动作；业务模块负责表达“仍引用/可删除”。这是下一轮结构变更，不属于 FIFO 补丁，需要完整的取消、重跑及晚到结果竞争测试。

## 必须保留的保护

- 删除前检查文件身份：同路径被新文件替换后不能误删。
- 数据库事务与原子文件发布边界、崩溃重放幂等。
- 取消/旧结果竞争的版本检查。
- 原图不可因派生产物回滚而被删除。
- 正在执行的文件动作与清理不能同时持有冲突路径。

## 推荐实施次序

1. 部署并观察本次 FIFO 与重复导入修复；记录每秒完成条目及剩余量。不能仅凭查询计划宣称 NAS 实际吞吐已改善。
2. 统一 Deferred/Failed 处理及重试唤醒，测试一个坏任务不阻塞后续任务、没有新通知也能重试、无忙循环。
3. 恢复时只读下一项授权数据，补多文件顺序和崩溃断点测试。
4. 收拢业务提交后清理与终态维护；最后处理业务表引用耦合。

审查覆盖了 schema/queries、Journal 状态与授权、恢复循环、后台消费者，以及 import 的发布与清理边界；尚未逐个证明所有业务调用者的安全性，不把上述建议当成已完成的全系统重写。
